# THIA to Seed Promotion Lane

> Scope: when a function integrated in THIA/D-ND should become part of
> `d-nd-seed`.

## Principle

THIA is the living runtime where functions are tested under real pressure.
`d-nd-seed` is where reusable invariants go after they have proven useful.

Do not copy THIA runtime state into the seed. Promote only the pattern that a
new node should inherit:

- the problem the function solves;
- the operating rule;
- the boundary and side effects;
- the minimal portable implementation or template;
- the verification shape.

The seed should not contain THIA secrets, runtime data, current packets,
operator-private transcripts, dirty worktree facts, or local service paths
unless they are clearly marked as examples.

## Promotion Test

Promote a THIA function into the seed when at least one of these is true:

- the function prevented a repeatable failure;
- the operator corrected a behavior and the correction should survive future
  nodes;
- the function is useful outside the current THIA instance;
- a new Lab or node should be born with that capability already present;
- the function changes boot, safety, memory, cascade, evaluation, translation,
  assistant boundary, or install behavior.

Do not promote when the function is still an experiment, depends on private
runtime state, contains domain-specific copy without a portable rule, or has
not been verified in the live territory.

## Promotion Targets

Choose the smallest target that preserves the invariant:

| THIA function shape | Seed target |
|---|---|
| Boot or reentry rule | `docs/boot_router.md`, `docs/boot_system_map.md`, hook template |
| Safety or destructive-action guard | `templates/hooks/safety_guard.sh.tmpl`, safety docs |
| Memory/continuum behavior | pre/post compact hooks, memory docs |
| Inter-node communication | `docs/cascade_trigger.md`, Sinapsi skill/plugin docs |
| Reusable assistant capability | skill template or plugin skill |
| Lab generation/runtime pattern | `docs/LAB_PATTERN.md`, Lab scripts, install assistant docs |
| UI/report language policy | docs + templates that generate UI contracts |
| New structural directive | `docs/directives_registry.md` entry or linked directive doc |

If more than one target is needed, write the directive first, then propagate
manually. Do not script mass injection into every file.

## Workflow

1. Identify the THIA source: file, commit, packet, operator correction, or live
   verification.
2. Extract the invariant: what should transfer without THIA-specific state.
3. Pick one seed target and write the minimal patch.
4. Add or update verification instructions.
5. Run syntax/checks available for the touched files.
6. Update `README.md` or `llms.txt` only when discoverability changes.
7. Commit only after reading the diff and confirming no secrets were copied.

## Current THIA Patterns That Belong Here

These are examples of functions that should end in the seed once stabilized:

- day-start boot router + continuum signal handling;
- public visitor vs authenticated admin/operator action boundary;
- explicit translation flow for report/artifact bodies while preserving source
  originals;
- MiniDash/admin surface contract for generated Labs;
- canvas or review-card flow that turns assistant output into editable material;
- Lab delete/cleanup dry-run manifest before destructive deletion;
- assistant prompt contract generated by a Lab installer.

## Boundary

The seed is not THIA's archive. It is the portable substrate.

If the next node needs to know the current THIA state, write or update THIA/TM7
memory. If the next node should be born with the capability, promote the
capability here.
